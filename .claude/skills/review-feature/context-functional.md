# 機能面レビュー コンテキスト

## 目的

docs に定義された仕様（ユーザーストーリー、画面遷移、API ルート、データモデル）と実際の動作を突き合わせ、不一致を発見する。

## レビュー手順

### Step 1: ドキュメントからチェックリストを生成

`docs/<feature>/user-stories.md` と `docs/<feature>/ui-ux.md` を読み込み、以下のチェックリストを自動生成する:

1. **ユーザーストーリーごとのフロー確認項目**
   - 各 sequence diagram のステップを確認項目に変換
   - 正常系と異常系（エラー、タイムアウト、バリデーション）を含める

2. **画面遷移の確認項目**
   - 各フェーズ間の遷移が正しいか
   - 戻るボタン、閉じるボタンの挙動
   - ブラウザのリロード後の状態復帰

3. **データモデルとの整合性**
   - `docs/<feature>/architecture.md` のデータモデルと実際の API レスポンスが一致するか

生成したチェックリストをユーザーに提示し、追加・修正があるか確認する。

### Step 2: Playwright MCP で正常系を確認

チェックリストの各項目を Playwright MCP で実際に操作して確認する。

**確認の進め方:**

1. 各ユーザーストーリーの正常系フローを最初から最後まで通す
2. 各画面で以下を確認:
   - `data-testid` で指定された要素が存在するか
   - テキスト内容が docs の記載と一致するか
   - ボタンの enabled/disabled 状態が正しいか
   - 画面遷移が docs の state diagram と一致するか
3. スクリーンショットを撮影して証拠を残す

**Playwright MCP の操作パターン:**

```javascript
// フェーズの確認
await page.getByTestId('<phase-testid>').waitFor();

// テキスト確認
const text = await page.getByTestId('<testid>').textContent();

// ボタン状態確認
const disabled = await page.getByTestId('<testid>').isDisabled();

// スクリーンショット
await page.screenshot({ path: '/tmp/review-<name>.png' });
```

### Step 3: 異常系・エッジケースを確認

以下のパターンをテストする:

1. **バリデーション**: 空入力、長すぎる入力、不正な文字
2. **ネットワークエラー**: API が 500 を返した場合の UI 表示
3. **セッション切れ**: トークン期限切れ後の挙動
4. **同時操作**: 複数タブ/ブラウザでの操作
5. **ブラウザリロード**: 各フェーズでリロードした場合の復帰

### Step 4: API レスポンスの検証

`docs/<feature>/architecture.md` の API ルート表と実際のレスポンスを比較する。

- 各エンドポイントに対して curl でリクエストを送る
- レスポンスのフィールド名、型、値の範囲が docs と一致するか
- ステータスコードが適切か（200, 201, 400, 401, 403, 404, 429）

## 発見事項の記録

各発見事項を以下の形式で記録する:

```
### [重要度] <タイトル>
- **場所**: <画面名 or API エンドポイント>
- **期待**: docs の記載: "<引用>"
- **実際**: 実際の動作: "<詳細>"
- **再現手順**: 1. ... 2. ... 3. ...
- **スクリーンショット**: (あれば)
```

## 判定基準

| 重要度 | 基準 |
|--------|------|
| Critical | 主要フローが完了できない。データの不整合が発生する |
| Warning | 仕様との不一致があるが回避策がある。エッジケースで問題が起きる |
| Info | 軽微な表示の差異。docs の記載が古い（docs 側の更新が必要） |
