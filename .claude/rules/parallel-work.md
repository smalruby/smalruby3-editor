# 並列で作業を進めるときの指針

サブエージェントやバックグラウンドのコマンドを並べて動かすときの目安。**決まった上限ではない**。
コンテナのメモリと CPU を見ながら、そのときどきで数を決める。

## なぜ

devcontainer は 8 GB・5 CPU ほどで、人間のホストの Docker の中で動く。重い処理を重ねると、
コンテナのメモリが尽きるだけでなく、ホストの動作ももたつく。実際に、エージェントが jest の
unit テスト全体を 4 ワーカーで流し（約 4.3 GB）、同時に別のエージェントが webpack でビルドして
（約 0.9 GB）、空きメモリが 100 MB を切ったことがある。

## 目安

- **重い処理を含む作業は、同時に 2 本くらいまで。** 重い処理とは、jest のまとまった実行、
  webpack のビルド、ブラウザ（Playwright / Selenium / dev server）を使う確認など。
  docs・Issue の整理・軽いコード読み・GitHub の操作だけの作業は、数に入れなくてよい。
- **始める前に `free -m` を見る。** available が 2〜3 GB を切っていたら、新しい重い作業は
  始めずに、いま動いているものが終わるのを待つ。足りなくなったら、重い作業から止める。
- **テストはローカルでは関係するファイルだけ。** jest は
  `npm exec jest -- --runInBand <file>`（多くても `-w 2`）。`test/unit` 全体はローカルで流さず
  CI に任せる（CLAUDE.md の Testing Strategy）。jest の設定（ワーカー数など）は変えない。
  scratch-vm の tap も関係するファイルだけ。
- **サブエージェントに頼むときは、上の 2 つ（関係するテストだけ・重いものを重ねない）を指示に書く。**
  エージェントは親の状況を知らないので、書かないと全体を流しがち。

## 後片付け

- 終わったら、自分が起動したプロセスが残っていないか確かめる
  （`ps -eo pid,rss,etime,args --sort=-rss | head`）。ブラウザは
  `pgrep -af 'chromedriver|chromium|headless_shell|webpack'`。
- 「終わるまで待つ」ループに `pgrep -f <パターン>` を使わない。ループ自身のコマンド行に一致して
  永久に終わらないことがある。待つときは、バックグラウンド実行の通知か `gh pr checks --watch` を使う。

## 臨機応変に

これは目安。メモリに余裕があり、作業が軽いなら 3〜5 本並べてよいし、重いビルドが走っているときは
1 本に絞ってよい。人間がホストのもたつきやメモリを指摘したら、すぐに数を減らす。
