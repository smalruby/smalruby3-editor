# 画面を変えるときは、動くモックアップで先に人間と同意する

画面の見た目・使い心地（UI・UX）を変える作業は、**実装を始める前に、動くモックアップを artifact で作り、
人間と同意してから**実装する。エディタ本体・autopilot のモニター・クラス管理など、どの画面でも同じ。

## なぜ

- 見た目の良し悪しは、文章では決められないことが多い。表や説明だけで決めると、作ってから「思っていたのと違う」になる。
- 動くもの（押せる・開ける・切りかえられる）を触ると、密度・色・動きの「感じ」を AI と人間で同じものとして話せる。
- 触って出てきた「感じ」を言葉にしてデザインシステムに残すと、次の画面で同じ相談をしなくて済む。

## やること

1. **モックアップを作る**: 本物に近いデータ（いまの Issue・作品など）を入れた、動く artifact の HTML。
   - 迷っているところは、**つまみ**（密度・行の高さ・色の濃さ・案 A / B の切りかえなど）にして、人間がその場で変えられるようにする。
   - 部分ごとに「良い / 気になる」と一言のコメントを残せるようにし、答えは artifact の db に保存して AI が読み返す。
   - ライト・ダークの両方、スマホの幅で崩れないこと。
2. **人間と同意する**: 答えとコメントを読み、直したモックアップをもう一度見せる。同意が取れるまで繰り返す。
   同意したモックアップの URL と、つまみの決まった値を Issue か PR に残す。
3. **言葉にしてデザインシステムに入れる**: 人間の「感じ」（例:「密だとうんざりする」「赤は落ち着かない」）を、
   **規則の文 + トークンの値 + 理由**にして、その画面のデザインシステム（エディタは `docs/design-system/`、
   autopilot は `docs/autopilot/` のモニターの節）に書く。モックアップのつまみで決まった値をトークンにする。
4. **実装する**: 同意したモックアップとトークンに合わせて作る。PR に、モックアップと実装のスクリーンショットを並べる。

## 例外

- 見た目が変わらない変更（色の直書きをトークンに置きかえるだけ、内部の作りの変更など）はモックアップ不要。
- 文言だけの直し、既存のデザインシステムの部品をそのまま使う小さな追加、不具合で崩れた見た目を元に戻す修正も不要。

## autopilot で進めるとき

- worker は、画面を変える Issue でモックアップがまだ同意されていなければ、実装せずにモックアップを作って
  人間に返す（HITL）。同意したモックアップの URL が Issue にあれば、それに合わせて実装する。
- 人間の確認は EPIC ごとにまとめる（`.claude/rules/human-wait.md`）。モックアップも、EPIC の画面をまとめて 1 つにしてよい。
