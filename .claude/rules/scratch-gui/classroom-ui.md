# クラス管理 — 先生の画面の UI 規約（R1〜R6）

クラス管理の**先生の画面**を新しく作る・直すときは、次の規約を指摘を待たずに守る。
レビューでも同じ観点で見る（外れていれば **[Must]**。理由があって外すときは PR 本文に理由を書く）。
**[Must]** にするのは、その PR が新しく書いた・直した箇所だけ。差分の外に残る既存の不一致は
**[FYI]** に留める（直すのは画面ごとの Issue。末尾の「既存の規約との関係」を参照）。

> 機能の仕様・画面ごとの文言は `docs/classroom/ui-ux.md`、data-testid は
> `docs/classroom/testing.md`、モーダルの背景色は `modals.md` が正。本ファイルは
> それらを置き換えず、「どう作るか」の共通の決まりだけを書く。

## お手本は Google Classroom

スモウルビーのクラス管理を使う先生は、Google Classroom を使いこなしている。**言葉と操作は
できるだけ Google Classroom に合わせ、独自の言い方や置き方を作らない。** 迷ったら
「Google Classroom ではどう書いてあるか・どこに置いてあるか」を先に調べる。

### 言葉の対応

| 使う言葉 | 使わない言い方 / 補足 |
|---|---|
| **クラスを作成** | 「クラスを作る」 |
| **［＋ 作成 ▾］→ 課題** | 「課題を作る」ボタンを単独で置かない |
| **［＋ 作成 ▾］→ トピック / トピックを追加** | 一覧の上の「新しいトピック」入力欄 |
| **課題を再利用** | 「前の課題を使い回す」 |
| **セクション** | Google Classroom と同じ。入力欄には例（「例: 1組、A コース（なくてもよい）」）を添える |
| **年度** | Google Classroom には無いが、学年とは別の値なので残す |
| **メンバー** | 「メンバー（座席）」 |
| **採点** | 「評価」。AI の評価・評価軸などの中の言葉は画面を作るときに合わせて見直す |
| **参加コード** | **スモウルビーの正式名称なのでそのまま**（課題ごとのコード）。Google Classroom の「クラスコード」に寄せない |

意味が違うものは無理にそろえない（そろえると誤解を生むものは、その画面の Issue で決める）。

## R1 入力欄には、いつも見えるラベルを付ける

- **何をする**: すべての入力欄に、欄の上か左に**常に見えるラベル**を付ける。プレースホルダーは
  **入力例だけ**（「例: 6年1組」）に使い、ラベルの代わりにしない。表示だけの値（一覧の行の
  参加コード・日付など）にも小さなラベル（「参加コード」「授業日」）を付ける。
- **なぜ**: プレースホルダーは値を入れると消える。設定画面に「2026」「8」「8ky49d」だけが
  並ぶと、何の値かは入れた本人にしか分からない。
- **レビューでの見分け方**: `placeholder` だけで `<label>`（または見える見出し）が無い入力欄。
  値を入れた状態のスクリーンショットで、各値が何か読めるか。`aria-label` だけ（見えない）も不可。

## R2 主な操作は 1 画面に 1 つ

- **何をする**: いちばんよく使う操作だけを主ボタン（青）にする。ほかの作り方は
  **［＋ 作成 ▾］のようなメニュー**にまとめ、まれな操作（一括ダウンロードなど）は「…」に入れる。
- **なぜ**: 同じ見た目のボタンが横に並ぶと、どれから押すのか分からない。先生によって使う
  作り方は違うので、1 つを決め打ちせずメニューで毎回選んでもらう。
- **レビューでの見分け方**: 1 画面に同じ重さ（同じ色・大きさ）のボタンが 3 つ以上並ぶ。主ボタンが
  2 つ以上ある。まれな操作が主ボタンと同じ列に並んでいる。

## R3 設定は 1 行の要約と現在の値

- **何をする**: 設定は「何を決めるか・何が起こるか」を **1 行の要約**と**現在の値**で見せ、
  詳しい説明は開いたときだけ出す。あまり変えない設定は「**詳しい設定**」に畳み、閉じた状態でも
  現在の値（「前回から: しない」など）を並べて既定値のままでよいことを示す。
- **なぜ**: 長い説明を地の文で並べると、画面が縦に伸びて主な操作が下に押し出される（R6）。
- **レビューでの見分け方**: 説明文が 2 行以上ずっと出ている設定。閉じた「詳しい設定」から
  いまの値が分からない。

## R4 赤は「いま対処が必要」なときだけ

- **何をする**: 赤（警告色・赤いボタン・赤い印）は、先生が**いま**対処しないといけないときだけ
  使う。保存期限は**残り 7 日以内**のときだけ赤にし、それより先は灰色の小さな表示にする。
- **なぜ**: 作ったばかりの課題にも赤い警告や赤いボタンが出ていると、本当に急ぐときに目立たない。
- **レビューでの見分け方**: 状態に関係なく常に赤い要素。保存期限の赤の閾値が 7 日以外。
  取り消せる操作（アーカイブなど）にまで赤を使っていないか。

## R5 色や記号の意味は、その場で分かるように

- **何をする**: 色・記号・アイコンで状態を表すときは、**凡例**を同じ画面に置くか、ラベルを付ける
  （座席の色、課題行の日付など）。
- **なぜ**: 座席の灰色と青、行の日付が何を意味するかが書いていないと、先生は推測するしかない。
- **レビューでの見分け方**: 色だけで区別している状態（色覚の違いでも読めるか）。
  凡例やラベルが別の画面・ツールチップの中にしか無い。

## R6 1300×600 で縦スクロール無し・確定のボタンが必ず見える

- **何をする**: 授業 PC の画面（**1300×600**）で、先生の画面も**縦スクロール無し**にする。
  保存・作成などの**確定のボタンがスクロールせずに見える**こと。収まらなければ項目を畳む（R3）か、
  **ステップに分けて 1 画面に 1 つの操作**へ寄せる。
- **なぜ**: 確定のボタンがスクロールの先にあると押し忘れが起き、「下の［保存］で確定します」の
  ような注意書きが増える。
- **DoD**: 1300×600 で開き、**主ボタンの下端の位置**（`getBoundingClientRect().bottom`、600 以下で
  あること）と、本文が `scrollHeight <= clientHeight` かを測って **PR 本文に書く**。
  `tools/playwright-verify/verify-classroom-viewport.mjs` は生徒の画面を厳密に測るが、先生の画面は
  「モーダルがはみ出さない」までしか見ないので、主ボタンの位置は別に測る（スクリプトを足してよい）。
- **レビューでの見分け方**: PR に主ボタンの下端の値が無い。スクリーンショットで確定のボタンが
  見えない。本文に縦スクロールバーが出ている。

## 既存の規約との関係

- `modals.md`: モーダル本文の背景色の決まりはそのまま守る（R1〜R6 と独立）。
- `classroom.md`: ファイル構成・ドキュメントの置き場所。画面の文言を変えたら
  `docs/classroom/ui-ux.md` を、data-testid を変えたら `docs/classroom/testing.md` を更新する。
- 生徒の画面は以前から 1300×600 でスクロール無しが必須（`verify-classroom-viewport.mjs` が測る）。
  R6 は同じ決まりを先生の画面にも広げたもの。
- 既存の画面には R1〜R6 にまだ合っていないところがある（例: 保存期限の警告は現在 30 日以下で出る）。
  直すのは画面ごとの Issue で行う。新しく書くコードは R1〜R6 に合わせる。
