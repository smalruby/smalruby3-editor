# 日本語モードの方針（共通テスト用プログラム表記）

> **🆕 Smalruby 独自** — upstream に存在しない、Smalruby のために新規追加された機能

日本語モード（コードや docs では「DNCL モード」と呼んでいる）を変えるときは、まずこの方針を読む。
文法・記号・変換の向きで迷ったときは、ここに書いた順で決める。

## 何に対応するのか

スモウルビーの日本語モードが対応するのは、大学入学共通テスト「情報I」で使われる
**共通テスト用プログラム表記**である。

- 共通テスト用プログラム表記には、まとまった仕様書が無い。大学入試センターは
  「あらかじめ公表する予定はありません」としている。まとまった説明は、
  「試作問題『情報』の概要」の「共通テスト用プログラム表記の例示」（以下「例示」）だけである。
- 文法ははっきり決まっていない。問題文の中で必要な補足をして、前提知識が無くても答えられるようにしている。
  例示も「この説明文書の記述内容に従わない形式で出題することもあります」と断っている。
- 試験で問われるのは、**問題の前提文を含めて、初めて見る書き方を読み解く力**である。
  0 からプログラムを書く力は問われない（記述式の問題は出ない）。

### DNCL は別のもの

大学入試センターの「共通テスト手順記述標準言語（DNCL）の説明」（2022 年 1 月）は、
**「情報関係基礎」**（専門学科・総合学科の受験者向け）のための言語の説明である。
情報I の共通テスト用プログラム表記とは別のものである。

| | DNCL | 共通テスト用プログラム表記 |
|---|---|---|
| 試験 | 情報関係基礎 | 情報I（2025 年〜） |
| 仕様 | 大学入試センターが説明資料を公開 | まとまった仕様書は無い。例示と、試作問題・過去問の例があるだけ |
| 代入 | `kosu ← 3` | `kosu = 3` |
| 表示 | `kosu を表示する` | `表示する(kosu)` |
| ブロックの終わり | `を実行する` / `を繰り返す` の行 | 行の左の縦線と、最後の行の L 字（例示・試作問題では `｜` と `⎿`） |
| かつ / または | `かつ` / `または` / `でない` | `and` / `or` / `not` |

- 情報I の問題で DNCL の書き方が参考にされることはある。しかし、**受験者が DNCL を知識として
  知っている前提の問題は出ない**。

### 呼び方

- **標準の形**: 共通テスト用プログラム表記の例題に合わせた日本語モードの書き方。行番号、
  左の縦線と L 字、`ならば:`、`=`、`表示する(...)`、`and` / `or` を使う。
  これまでコードと docs で「DNCLv2」と呼んでいたものは、これにあたる。今後は「DNCLv2」と呼ばない。
- **DNCL 風の形**: いまの日本語モードが、ブロックや Ruby から日本語にするときに出す書き方。
  ブロックの終わりを `を実行する` / `を繰り返す` / `と定義する` の行で閉じ、`かつ` / `または` /
  `でない` を使う。これまで「Smalruby DNCL」と呼んでいたもの。
- 「DNCL」とだけ書くときは、情報関係基礎の DNCL のことか、情報I の共通テスト用プログラム表記の
  ことかを区別して書く。

## 日本語モードの目的

日本語モードは、**プログラムを読む力をつけるための機能**とする。書きやすさより、問題文の
プログラムをそのまま読めること、動かして確かめられることを優先する。

### 支える読み方

共通テストの問われ方は、多い順に、空欄を埋める、表を手で埋める（トレース）、実行回数を答える、
行を差し込む位置を選ぶ、である。どれも、問題文が行番号でプログラムの行を指して問う。
日本語モードは、この順で次のことを支える。

1. 行番号と罫線を残したまま読めて、そのまま動かせる。
2. 行番号で行を指せる（エラーや説明が、問題と同じ行番号で出る）。
3. 1 行ずつ、変数の値の変化を追える（トレース）。
4. ある行が何回実行されたかを数えられる。
5. 空欄を埋めたり、行を差し込んだりして、結果を確かめられる。

出力を予想する問い、誤りを見つける問いは、公式の問題にはまだ出ていない。支えるものを増やすときは、
公式の問題に多い問われ方を先にする。

## 例題の範囲と重み

- 文法の決め方でいう**「例題」は、大学入試センターの公式の資料だけ**とする。
  - 例示、サンプル問題、試作問題、本試験・追試験の問題。
- 教科書会社・予備校・大学の学習環境などの**非公式の資料は、補助にだけ使う**。
  - 公式に無い記法の候補を探すとき（下の決め方の ② と ⑤）。
  - 読むとき（貼り付けなど）に受け付ける揺れを知るとき。
  - 非公式の資料には、DNCL と混ぜた書き方や、実装ツールの独自の拡張も多い。件数が多くても、それだけで採らない。
- 公式の問題の中で、**意味が同じ書き方が年度によって揺れるときは、いちばん新しい年度の本試験・追試験に合わせる**。
  - 例示は、問題文に約束が無いときの既定の解釈として使う（例: 添字は、問題文に説明が無ければ 0 から）。

## 文法の決め方（優先順位）

共通テスト用プログラム表記には決まった文法が無いので、次の順で決める。**DNCL は、困ったときに
参照するもの**であり、実際の書き方（`=`、`表示する(...)`、罫線など）は例題に合わせる。

1. **まず例題から標準的な文法を見出す。** 例題（公式の資料）を集めて、共通の書き方を探す。
   意味が同じ書き方の揺れは、上の「例題の範囲と重み」のとおり、新しい年度の問題に合わせて 1 つにする。
2. **例題に記載が無いものは、DNCL に従う。** このとき、DNCL からは言葉（「関数」「になるまで」
   「のすべての要素に」など）を借り、**見た目は例題に合わせる**。
   - 見た目とは、行の終わりの `:`、左の罫線、`=`、`( ... )` の呼び出しの形のこと。
   - 例: 関数の定義は `関数 名前(引数):` で始め、中の行を罫線で示し、`と定義する` の行は置かない。
3. **例題に揺れがあって一意に決まらず、DNCL に該当する記載があるときは、DNCL に記載がある
   ものを採用する。** 「一意に決まらない」とは、新しい年度の問題でも決まらないこと（新しい年度に
   出てこない、または新しい年度の中でも揺れる）をいう。
4. 例題に揺れがあって、DNCL にも該当する記載が無いときは、例題の書き方の中から、もっとも
   DNCL に近いもの、または Ruby の書き方に近いものを選ぶ。
5. **例題にも DNCL にも記載が無いもの**（戻り値を返す文、配列への要素の追加、繰り返しを途中で
   抜ける文など）は、非公式の資料の多数派か、Ruby の書き方に近いものから選ぶ
   （例: 戻り値は `値 を返す`）。見た目は ② と同じく例題に合わせる。
6. 決めた理由を Issue か PR に残す。
   - 理由とは、どの例題を見たか、ほかにどんな書き方があったか、DNCL のどこを見たか、非公式のどの資料を見たか。

問題文が意味を約束するもの（添字の始まりなど）は、この順で 1 つに決めずに、下の「設定」にする。

## 設定にするものと、1 つに決めるもの

問題によって書き方が違うので、文法の一部を設定で選べるようにする。
何を設定にするかは、次の基準で分ける。

| 種類 | 扱い | 例 |
|---|---|---|
| **意味が変わるもの、または問題文で約束されるもの** | **設定にする**。選んだ設定はプログラムの冒頭に説明文として書く | 添字の始まり（0 から / 1 から）、コメントの記号（`#` か `//` か。`//` をコメントにしたときは、`//` を整数の割り算に使えない）、論理演算子の書き方 |
| **意味が変わらない、見た目だけの揺れ** | **設定にしない**。読むとき（貼り付けなど）はどの書き方も受け付ける。書くとき（ブロックや Ruby から日本語にするとき）は 1 つにそろえる | 行番号の形（`(01)` / `(1)`）、罫線の文字（`｜` `⎿` / `|` `└`）、`:` と `：`、全角と半角の演算子（`＋` `％` `＜`）、引き算の記号（`-` / `−` / `–`）、`,` の後の空白 |

- 書くときにそろえる 1 つは、上の「文法の決め方」で決める（新しい年度の問題に合わせる）。
- 専門的でない受験者には細かい設定が難しいので、**よくある設定のパターンを用意**する。
- プログラムは、選んだ設定に従った文法で表される（Ruby やブロックから日本語にするときも）。
- 設定の項目、パターン、設定をどこに保存するかは、基本設計で決める。

## 冒頭の説明文

選んだ設定は、プログラムの冒頭に説明文として書く（問題文の前提の説明と同じ役目）。

- **言い回しは、公式の問題文の約束の型に合わせる。** 常体で書き、読点は「，」を使う。
  問題文と同じ形の文を読むことが、試験で前提の説明を読む練習になる。
  - 添字: 「すべての配列の添字は 1 から始まる。」（例示・本試験の「〜の添字は 〇 から始まる」の型）
  - 論理演算子: 「「and」は「かつ」を意味する論理演算子であり，左右の式がともに真のときにだけ真となる。」の型
  - 用意された関数: 「名前(引数)…説明。」と「例えば，…は 〇 となる。」の 2 段の型
- **問題の中で説明されない約束は書かない。** 罫線の意味、`表示する`、`=` の意味は、公式の問題でも
  説明されない。冒頭には、問題文で約束される種類のことだけを書く。
- 説明文をコメントにするか専用の行にするかは、基本設計で決める。

## いまの実装からの移り方

- 表示と書き出し（ブロックや Ruby から日本語にするとき、生成AI に相談の答えの形）は、**標準の形に切り替える**。
- **DNCL 風の形も、読み込みは続ける。** 既存の教材、docs、生成AI の答え、利用者の手元のテキストが、そのまま動くようにする。
- DNCL 風の形を、設定のパターンの 1 つとして残すかどうかは、基本設計で決める。
- 細かい手順（いつ、どの順で切り替えるか）は、基本設計で決める。
  - 作品がブロックとして保存されていて、表示を変えても作品が壊れないことも、そこで確かめる。

## AI と autopilot が守ること

- 日本語モードの文法・記号を足したり変えたりするときは、DNCL の説明資料だけを根拠にしない。
  - 公式の例題（例示・試作問題・過去問）で使われているかを確かめ、上の「文法の決め方」に従う。
  - 非公式の資料は補助にだけ使う。
- 「DNCL」と書いてあっても、情報関係基礎の DNCL のことか、情報I の共通テスト用プログラム表記の
  ことかを区別して書く。日本語モードの書き方は「標準の形」「DNCL 風の形」と呼ぶ。
- 大学入試センターの試験問題の著作権はセンターにある。二次利用（複写して配る、問題の一部や全部を
  使った問題集を作る。インターネット上も含む）には、センターへの利用申請が要る。
  予備校などのサイトに載っている問題も、問題そのものの権利はセンターにあると考える。
  - Issue・PR・docs では、記法を示すのに要る数行だけを引用し、出典（発行者・URL・年度・問題番号）を付ける。
    問題文の全文や図の全体は載せない。
  - 実際の問題を、そのままテストのデータや教材としてリポジトリやスモウルビーに入れない。
    テストや教材には、記法をまねて自分で作ったプログラムを使う。
  - 実際の問題を教材に使いたいときは、人間がセンターへの利用申請を判断する。
