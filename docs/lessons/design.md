# レッスンの設計方針

> **🆕 Smalruby 独自** — upstream に存在しない、Smalruby のために新規追加された機能

レッスン（コース › レッスン › チャレンジ）で**決めたこと**と、**そう決めた理由**をまとめる。
コースやチャレンジを足すとき、画面を直すときは、まずここに沿っているかを確かめる。方針を変えるときは、
先にこのファイルを直してから実装する（実装の詳細・データの形・data-testid は [`README.md`](README.md)）。

## 目的

- 先生の説明がなくても、順番にやればスモウルビーでのプログラミングのやり方が身につくこと。
- 探すための一覧ではなく、「何をやって、どこまでできたか」が見えること。
- 設計の出発点: 中学 2 年のチャットアプリの授業で、スプライトを足す・押したら反応する、といった基本が
  できなかった。先生なしで基本を一通り身につける入口が要る。

## 使われる場面（前提）

- **授業のパソコンは 1300×600**。レッスン表・課題バー・ヒントは、この大きさでスクロールせずに使えること。
  対象はステージが**小・中サイズ**のとき（中が既定）。**大サイズは対象外**。1300×600 で大きいステージを選ぶと、ステージの下のスプライトの
  領域が画面の外に出るが、それは選んだ生徒側で（ブラウザ全体のズームを変えるなどして）対応する前提とし、
  スモウルビーでは何もしない。
- **先生がプロジェクターに映して説明する**。課題の全文は大きめの字で、画面に出したままにできること。
- **共用のパソコン**が多い。記録は端末に残し、段 2 でクラスの課題に引き継ぐ。
- SP（スマホの縦・横）でも使える。ただし主な対象は授業のパソコン。
- 小学 3 年生以下は主な対象にしない。文言は漢字まじりの普通の日本語（ひらがなだけの表示は `ja-Hira`）。

## 階層と名前

| 階層 | 画面での表し方 | 決まり |
|---|---|---|
| 言語 | レッスン表の上の帯のボタン | ブロック／Ruby／日本語（DNCL）。**コースがある言語のボタンだけ出す**（いまは「ブロック」だけ） |
| コース | 大きい見出し | 全部できたら名前の前に ✓。右にプログレスバーと「n / 全部」（課題のチャレンジだけのレッスン表では出さない） |
| レッスン | コースの中の小さい見出し | 「レッスン 1」＋ 名前。1 つのレッスンは 3〜4 個のチャレンジ（「チャットをつくろう」だけは 5 個まで） |
| チャレンジ | カード | 1 つ 5 分・3〜5 ブロックで作れる大きさ。チャレンジの ID は一度出したら変えない（記録のキー） |

- 最初のコースはブロック › 「きょうからプログラマー」（はじめての人が全員やる）。
  レッスン 1「うごかしてみよう」（1〜4）、レッスン 2「えらんで たずねよう」（5〜7）、
  レッスン 3「おぼえて つたえよう」（8〜11）。分け方は「覚えること」のまとまり
  （きっかけと動き・見た目・音／条件と入力／変数・メッセージ・リスト）。
- 中学 2 年の授業のためのコースはブロック › 「チャットをつくろう」（下の[「チャットをつくろう」](#中-2-のコースチャットをつくろう)）。
- レッスンを分け直しても、チャレンジの ID と記録は変えない。記録はチャレンジ ID を主にし、
  どのレッスンに属するかは、いまの定義から読みかえる。

## 段 1 で入れないもの（入れないと決めたもの）

| 入れないもの | 理由・代わり |
|---|---|
| **「必須」** | レッスン単体では必須の理由を生徒に説明できない。**クラスの課題とレッスンを紐付けて、先生が必須にしたときだけ**必須のふるまいをする（段 2）。コースのバーは分けず、必須の残りは[段 2](#段-2-クラスの課題とレッスン)の課題の帯の文で伝える |
| **「できること」の一覧** | メンテナンスし続けるのが難しい。バッジなどのゲーミフィケーションを考えるときにあらためて作る |
| **「クリア！」「プログラマー デビュー！」などの言葉** | コースごとに言葉を決めるのが難しい。コース名の前の ✓ だけにする |
| **「レッスンをはじめよう！」などの誘う吹き出し** | どの端末にも出さない。レッスンに入る道は、メニューの「レッスン」と、段 2 の「課題にレッスンを紐付けたときだけ、クラスに参加して『はじめる』を選ぶとそのコースを開く」 |
| **カードの絵（イラスト・スクリーンショット）** | 描き続けるのが難しい。名前と単色だけにする（下の「カード」） |
| **スクリーンショットを使ったヒント** | 古くなる。ヒントの吹き出しには本物のブロックを描く |

## レッスン表

- **見た目はスモウルビーの「スプライトを選ぶ」画面と、Scratch の「チュートリアルを選ぶ」画面に近づける**。
  児童・生徒は見慣れていて、いまどれが選ばれているか（オレンジのボタン）、あとから Ruby などが押せる
  ようになることが伝わる。
  - 紫のヘッダー（← 戻る ／ 「レッスンを選ぶ」）。その下の薄い紫の帯に、検索 ＋ 区切り ＋ 言語のボタン。
  - その下に、コースの見出し → レッスンの見出し → チャレンジのカード。
- **1300×600 で、いまのコース（3 レッスン 11 枚）がスクロールせずに見える**こと。カードを足す・大きく
  するときはこれを確かめる。
- **例外: ブロックのコースが 2 つ以上になったら、レッスン表は自分の枠の中で縦にスクロールしてよい**（1300×600 でも）。
  スクロールしてよいのはレッスン表の枠の中だけで、生徒の画面のほかの部分（課題バー・ヒントなど）は、いまのとおり
  スクロールせずに使えること。コースが増えると、すべてを 1 画面に収めることはできないため。
- **検索**: チャレンジの名前の部分一致。合うものが無いレッスン・コースは隠す。大文字小文字・全角半角・
  カタカナとひらがなは区別しない。
- **増えたとき**: 1 ページに縦に並べる（コースが少ないあいだは、いちばん見わたしやすい）。コースが 4 つを
  超えたら、帯の 2 段目にコースのボタン（押すとそのコースまでスクロール）を出す。さらに増えたら
  「コースのカード → コースのページ」の 2 段階の入口を足す（いまのページがそのままコースのページになる）。
- SP: 帯は 1 行に収め、はみ出すボタンは横にスクロール。カードは縦で 2 列。

### カード

- **形: 左にブロックの色の帯、右に名前（横長）**。背が低く、カードが増えても場所を取らない。
- **色: そのチャレンジで多く使うブロックの色**。数え方:
  - 「プログラムを入れる」で入る、できあがりのプログラム（ほかのスプライトの分も）を、ブロックにして数える。
  - 形のあるブロックはすべて数える（帽子のブロック・値のブロックを含む。数の入力などの白い穴は数えない）。
  - **同じ数で並んだら、そのチャレンジで覚えるメインのブロックの色**にする。
  - 色はブロックのなかまの色そのまま。拡張機能は拡張の緑。
  - 例: 「キーで音を鳴らそう」はサウンド 2・イベント 1 → サウンド。「矢印キーで動かそう」は動き 2・イベント 2 で
    同数 → メインの動き。
- できたら ✓。「次のチャレンジ」で開いたときは、次にやるカードに「次はこれ！」。

## チャレンジ

- **毎回、新しい作品から始める**（前のチャレンジの続きにしない）。例外は「チャットをつくろう」のレッスン 4・5
  （下の[「5 つのレッスン」](#5-つのレッスン)）。
- パレットは使うブロックだけ（`allowedBlocks`）。ブロックの初期値は、仕様の表記（`[1 ▼]`・`(3)`）に合わせる。
  子どもが作る名前（変数・リスト・メッセージ）の ▼ には初期値を入れない。
- 英語の UI では、子どもが作る名前も英語にする（`count` / `talk` / `hello` など）。判定はどの言語の名前でも通す。
- **「できた」の判定はプログラムの形を見ない**。`uses`（決めたブロックが動いた）と `result`（変数・リスト・
  言った文字などの結果）だけ。答えのプログラムを入れて動かしても「できた」にする（区別しない）。

## 課題バー

- 上に課題の 1 行と「何個め / そのレッスンの全部」（レッスンの中の番号）。
- **画面の幅いっぱい**（エディタの列だけでなく、ステージの列の上もおおう）。「ヒント」「ほかのチャレンジへ」は
  **画面の右端**に置く。ステージの列（旗・止める・ステージの大きさ）は帯の下に下がり、そのまま押せる。
  縦が 40px 減る分は、中サイズのステージのスプライトの情報を詰め（`docs/sprite/README.md`）、右下のステージの列の
  見出し「ステージ」を出さないで補う（`docs/stage/README.md`）。ステージの列の見出しを消してもステージ（canvas）の
  位置は変わらないので、下の resize の決まりには当たらない。
- **ステージの列を（大きさを変えずに）上下左右に動かす変更は、動かしたあと window に `resize` を送る**。
  ステージは canvas の位置を resize / scroll のときにしか測り直さず、送らないとマウスの座標がずれて
  「マウスのポインターに触れた」が真にならない。課題バーが出る・消えるときは `containers/lesson-mode.jsx` が
  送っている。段 2 でバーを 2 本にするなど、レッスンの途中でバーの高さが変わるときも同じく送る。
- **全文はマウスを乗せたら下に出す**（課題が長くても短くても。改行もそのまま。小さな画像も出せる）。
  「全文」ボタンは置かない。SP では課題の文のタップで開き、もう一度で閉じる。
  - ヒントの吹き出しが出ていても、乗せれば全文を上に重ねて出す。メニューバーのメニューが開いているときと、
    「できた！」が出ているときは出さない。
- 課題の文は、読みやすい位置で改行しておく（定義の改行をそのまま出す）。
- 「やめる」とは書かない。前向きな言葉（「ほかのチャレンジへ」）にして、押すとレッスン表を開く。
- **右端に「レッスンをおえる」**（「ほかのチャレンジへ」の右）。「ほかのチャレンジへ」より目立たせない
  （透明地に白い枠）。押すとレッスンから出て、いまのプログラムを残したまま、ブロックを全部使えるいつもの画面に
  もどる（レッスン表は開かない・確認は出さない）。レッスンにもどるのはメニューの「レッスン」から。
  「できた！」の表示には入れない。

## ヒント

- 吹き出しの中に**本物のブロック**を描く。スポットライト（周りを暗くする）は、はじめて開いたチャレンジの
  基本操作だけ。
- **帽子のブロックを置く手順を抜かさない**。できあがりのプログラムにある帽子のブロック（「〜キーが
  押されたとき」「旗が押されたとき」「このスプライトが押されたとき」「〜を受け取ったとき」など）は、どれも
  どこかのヒントで置き方を示す。「〜の下に〜をつなげよう」と言う前に、その上のブロックを置くページがあること。
  「〜したら〜するプログラムを作ろう」のように 1 ページでまとめるときは、絵に帽子のブロックから描く。
- **絵は、そのページで置いてほしいブロックを、置いてほしい並びのまま描く**。文言で「〜と〜を入れよう」
  「2 組」「上と下に」と言うなら、その全部を、組み立てたときの並び（つながり・入れ子）で描く。一部だけを
  描くと、何をいくつ置くかが伝わらない（例: 「繰り返す」の中の「背景を Canyon にする・1 秒待つ・背景を
  Arctic にする・1 秒待つ」）。絵の無いページ（タブ・ステージ・キーを指すもの）はこの限りでない。
- **つなげる相手・置く位置を言うページは、相手のブロックもいっしょに描く**。「〜の下につなげよう」「〜の上に
  入れよう」「〜の中に入れよう」「穴に入れよう」なら、置くブロックだけでなく、相手（すぐ上のブロック・入れる先の
  ブロック）とつないだ並びで描く（例: 「ずっと」だけでなく「旗が押されたとき＋ずっと」、「タイマーをリセット」だけで
  なく「タイマーをリセット＋聞いて待つ」）。描くのは相手と置くブロックまでで、スクリプト全体にはしない
  （吹き出しが大きくなりすぎないように）。
- **「できた」になる操作を促すヒントを、手順の最後（「うまく動かないときは」のページの前）にする**（キーを押す・ステージのスプライトを押す・旗を押す・
  答えを入れるなど、課題を試すページ）。できたら吹き出しが閉じるので、そのあとのヒントは見られない。
  ブロックの消し方のような「知っておくとよいこと」も、試すページより前に置く。試すページは、ステージ・
  キーボード・旗を指す。
- **チャレンジを始めたら、ヒントの 1 ページ目を自動で開く**（ヒントボタンに気づかない子のため）。
- **ドラッグで動かせる**（じゃまなとき）。画面の外には出さない。
- 最後のページ（うまく動かないときは）:
  - 「プログラムを入れる」とは書かない。**「正解のプログラムを確認する」**にして、押すと
    「正解のプログラムで置き換えますか？あなたが作成したプログラムは消えます」［いいえ］［はい］を出す。
  - 進めるボタンは「おわり」。押すと閉じて、次に開くときは 1 ページ目から。
- **できたら吹き出しを閉じる**（「できた！」と「次のチャレンジ」を見てほしいため）。

## 「できた！」のあと

- 生徒に「次に何をすればよいか」がわかるようにする。字は大きく、出ている理由がひと目でわかるようにする。
- **チャレンジの名前は出さない**（課題バーに出ている）。「クリア！」などのことばは使わない。
- **チャレンジの終わりとレッスンの終わりを見分けられるようにする**。3 つの場面:
  1. **チャレンジができた（レッスンの途中）**: 大きく「できた！」。その下に、レッスンの中のできた数を丸で
     （できた = 塗り、いまできたもの = 塗り＋強調）と「このレッスンは、あと n つ」。ボタンは「次のチャレンジへ」
     （レッスン表のいまのレッスンを開き、次にやるチャレンジに「次はこれ！」）。色は青。
  2. **レッスンのチャレンジが全部できた（まだ全部できていないレッスンがある）**: 「できた！」と同じ大きさで
     「レッスン n ぜんぶできた！」、丸は全部塗り、2 行目「「レッスン名」の n つ、全部できました」。
     ボタンは「次のレッスンへ」（まだ全部できていない次のレッスンをレッスン表で開く）。**枠とボタンはお祝いの
     オレンジ**、アイコンは 🏆。
  3. **レッスンが全部できて、ほかに残っているレッスンが無い**: 2 と同じ形で、2 行目「「コース名」のレッスンは、
     これで全部です」、ボタンは「レッスン表へ」。後ろのレッスンは全部できていても前のレッスンを飛ばしているときは、
     「これで全部です」とは言わず 2 行目をレッスン名の行にする（ボタンは「レッスン表へ」のまま。飛ばしたレッスンは
     レッスン表で選ぶ）。
- × は置かない。2 つめのボタン「もう少し見る」（白地に枠）で閉じるだけ。次へ進むときは課題バーの
  「ほかのチャレンジへ」。

## 段 2 以降への申し送り

- **入口・必須・記録の引き継ぎ**: 下の「段 2: クラスの課題とレッスン」で決めた。
- **Ruby・日本語のコース**: コースができたら言語のボタンを出す。レッスン表の形は同じ。
- **「できること」の一覧・バッジ**: ゲーミフィケーションを考えるときに、あらためて設計する（段 2 でも扱わない）。

## 段 2: クラスの課題とレッスン

先生がクラスの課題にレッスンを紐付け、**必須**と**完了の条件**を決め、生徒の**進み具合**を見られるようにする。
授業で先生が、だれがどこで止まっているかを見て声をかけられるようにするため。これまでの「提出した／していない」の
2 択に、「どのチャレンジまで進んだか」が加わる。

ここにはレッスンの側の決まりを書く。先生の画面（説明タブ・座席・「進み具合」タブ・パネル）、生徒のクラスの画面、
CSV と採点は [`docs/classroom/ui-ux.md`](../classroom/ui-ux.md) の「レッスンの課題」に書く。

### 課題とレッスン

- **新しい課題の種類は作らない**。いまの課題に「レッスン」欄を足す。レッスンを選ばなければ、いままでの課題のまま。
- 1 つの課題に**コースは 1 つ**。レッスンにチェックすると中のチャレンジが全部入り、チャレンジごとに外せる。
  対象のレッスンは複数選べる。
- チャレンジの順番は**レッスンの順のまま**（先生は並べかえない）。
- 「**作品の提出もする**」を ON / OFF できる。ON のとき、提出は**課題につき最後の 1 回**。レッスンごとには求めない。

### 入口

- レッスンに入る道は 2 つだけ。**メニューの「レッスン」**と、**レッスンを紐付けた課題に参加して「はじめる」**。
  「レッスンをはじめよう！」の吹き出しは出さない（段 1 と同じ）。
- **「はじめる」**: レッスン表を課題のコースで開き、**課題のチャレンジだけ**を出す。課題の外のチャレンジは出さない。
  先生がチェックを外すのは「情報量を減らしたい」という意思表示なので、それに従う。
- **課題に参加したまま、メニューの「レッスン」から開いたとき**: コース全体を出し、上に**課題の帯**を載せる。
  課題の外のチャレンジもできる（記録は端末に残るが、クラスには送らない）。
- 参加完了の画面で、この課題がレッスンの課題であることと、作品も提出するかを先に伝える
  （生徒の「提出ボタンがありません」という質問を減らすため。文言は ui-ux.md）。
- レッスンの課題の「はじめる」は、いつもレッスン表を開く。スターターの無いレッスンの課題では、「どこから始めますか？」
  （スターター・前回の提出物）は出さない。スターターもある課題だけ、いままでの選択肢を「はじめる」と並べて出す
  （チャレンジは毎回新しい作品から始まるので、スターターや前回の提出物は、課題クリアのあとの作品づくりにだけ使う）。
- 課題のチャレンジを開いたときだけ「課題から開いた」とする（GA の計測・クラスへ送る分）。課題のチャレンジから
  「ほかのチャレンジへ」「次のチャレンジへ」を押したときは、レッスン表をまた課題のチャレンジだけで開き、
  次にやる課題のチャレンジに「次はこれ！」を付ける。まだできていないのが、いま出てきたチャレンジだけなら、それに付ける。

### 必須

- **レッスン単体では**（クラスの課題と紐付けないとき）、必須マークも必須のふるまいも出さない（段 1 と同じ）。
- **先生が課題で ★ を付けたチャレンジだけ**が必須になる。★ は選んだチャレンジにだけ付けられる。0 個でもよい。
- レッスン表のカードでは、★ はカードの**右**に出す。
- 必須が終わっていないことは、先生の表で別に見える。採点では減点しない（できた分の合計のまま・ui-ux.md の「採点」）。
- 段 1 で申し送った「必須があるときだけ、コースのバーを『必須』と『そのほか』の 2 本に分ける」は、課題の帯では
  **分けない**。必須の残りは帯の文の「（★ R つ）」で伝える（下の「課題の帯」）。

### 完了の条件

- 課題ごとに「**全部**」か「**n つ（必須をふくむ）**」を選ぶ。既定は「全部」。
- 「n つ」の n は、必須の数から選んだチャレンジの数までにする（必須より少ない数は選べない）。
- **「前からできた」（課題の前から端末にできた記録があったもの）も、条件の数に入れる**。課題ごとに入れる／入れないを
  切りかえる設定は作らない。やっていればその分お得、という考え方。
- 条件を満たすことを「**課題クリア**」と呼ぶ。課題は先生が決めた区切りなので、段 1 で使わなかった「クリア」を
  ここでは使う。

### 課題の帯

- レッスン表の上に、課題の帯を出す。帯は **1 行の文**にする:
  `［課題］<課題名>　条件: 6 つ　あと 5 つ（★ 5 つ）で課題クリア`
  - 「あと **N** つ」= **max（条件の数 − できた数, 残っている必須の数）**（課題クリアまでの残り。必須が残っていれば
    必須の数より減らない）。「★ **R** つ」= 残っている必須の数。
  - 必須が残っていなければ「（★ R つ）」は出さない（「あと 2 つで課題クリア」）。
  - 課題クリアのあとは「✓ 課題クリア」。
  - チャレンジごとの丸は**帯に出さない**。どのチャレンジができたか・必須かは、カードの ✓ と ★ で分かるため。
- 課題クリアのあと、作品も提出する課題では、帯に提出の案内（下）と［課題を提出する］を出す。
- **「はじめる」で開いた課題のチャレンジだけのレッスン表では、コースの進み具合（コース名の横のバーと「n / 全部」）を
  出さない**。課題の帯がその役目をする。コース名の見出しは残す。メニューの「レッスン」からコース全体を
  開いたときは、コースの進み具合を残し、課題の帯は同じ 1 行の文にする。
- チャレンジの中（課題バー）では、課題のチャレンジのときだけ、課題バーの**同じ行**に小さな帯を出す。中身は帯の文の
  短い形「あと 5 つ（★ 5 つ）」（必須が残っていなければ「あと 2 つ」）・課題クリアのあとは「✓ 課題クリア」で、丸は
  出さない。行を足さず、バーの高さは変えない（そのため `resize` の決まりには当たらない）。
- 課題の帯の提出の案内と［課題を提出する］は、クラスの画面とそろえて、**はじめて提出するまで**出す。
- クラスの画面の「進み具合」の行（丸・「4 / 6 できた」・「★ あと 1」）とメニューバーの印は、帯とは別にいまの形のまま。
- 課題の帯の数え方（あと N つ・★ R つ・できた数・課題クリア・メニューバーの印）は
  `packages/scratch-gui/src/lib/lessons/assignment-progress.js` の純粋関数にまとめる（帯の文の数は
  `assignmentRemainingParts`）。先生の画面（座席の色・
  「進み具合」タブ）も同じ関数で数える。

### この版に無いチャレンジ

サーバーはコースの中身を知らないので、先生が新しい版で選んだチャレンジ（生徒のタブが古い版のまま開いているなど）が、
生徒の端末のコースに無いことがある。

- 知らないチャレンジは**丸（クラスの画面）・できた数・条件から外す**（開けないので）。条件の数は、知っているチャレンジの数で止める。
  そうしないと「全部」の課題がいつまでも課題クリアにならない。
- 知らないチャレンジがあるときは、クラスの画面と課題の帯に「**新しいレッスンがあります。ページを読み込み直してね**」と出す。
- 作品も提出する課題では、知らないチャレンジがあれば、課題クリアの前でも［課題を提出する］を出す（提出できなくなるのを防ぐ）。
- 知らないチャレンジだけの課題は、課題クリアにしない（何もせずに ✓ にならないように）。

### 課題クリア

- 条件を満たしたチャレンジの「できた！」は、**「課題クリア！」**にする。段 1 の「レッスン n ぜんぶできた！」より優先する。
- 形は段 1 の 2・3 と同じお祝いの形（オレンジの枠とボタン・🏆）にそろえる。
- **作品も提出する課題**: 「課題クリア！」の下に「**レッスンで学んだことをつかって、自由にプログラムをつくろう。
  できたら作品を提出しよう**」と出し、主ボタンを「**課題を提出する**」にする。同じ案内は、クラスの画面と
  レッスン表の課題の帯にも出す。案内を出すのは**完了の条件を満たしたとき**から。
- 作品を提出しない課題: 主ボタンは段 1 と同じ（次のレッスンへ／レッスン表へ）。
- 課題クリアのあとにできたチャレンジは、ふつうの「できた！」に戻す（課題クリア！は 1 回だけ）。

### 本人の確認

共用のパソコンでは、端末に残っている記録が前に使った人のものかもしれない。そのまま送ると、先生の表に
ほかの人の記録が出る。

- **その課題ではじめて送るとき**、課題の対象のチャレンジの記録が端末にあれば、**一度だけ**
  「**あなたがやった記録ですか？**」と聞く。課題の前の記録が無ければ聞かない。
- 「**わたしの記録です**」→ 送る。先生の表では「前」（課題の前からできていた）として見える。
- 「**ちがう**」→ すぐには消さず、**もう一度確かめる**（判断できない生徒が多いため）。文言で決め方を伝える:
  「**自分のパソコンなら**消さずに戻って『わたしの記録です』を選ぼう。**みんなで使うパソコンなら**消そう」。
  - ［戻る］→ 1 つめの確認に戻る。［消す］→ 送らずに、**端末のレッスンの記録を空にする**。
- 答えはその課題について端末に覚え、同じ課題では二度と聞かない。覚える単位は**課題 × 席 × 席に入った人**
  （サーバーは席の人が入れ替わると行を作り直すので、それに合わせる）。席に入った人は、その端末で参加した時刻
  （セッションの `joinedAt`。参加するたびに変わる）で見分け、無ければセッショントークンの短いハッシュで見分ける
  （トークンそのものは残さない）。だから、共用のパソコンで同じ課題・同じ席に別の人が入ったときも、同じ生徒が
  入り直したときも、もう一度聞く。端末に覚えるのは新しいものから 50 件まで（localStorage
  `smalruby:lessonAssignmentConsent`）。
- 「前」にするのは、**一覧に出して「わたしの記録です」と答えた記録**。課題に参加したあとにできたものは「前」にしない。
  「前」にする記録の ID は答えと一緒に端末に覚え、はじめての送信が失敗しても、次の送信で同じものを「前」として送る。
  一覧には、この版のコースにあるチャレンジだけを出す（無いものは見せられないので、同意もしていないことにして送らない）。
- **同意していない記録は送らない**（1 つの決まり）: できた日時が答えた日時以前で、「前」にした記録に無いものは、
  前に使った人のものかもしれない。
  - 答えが「わたしの記録です」か、はじめて送るときに記録が無かった（聞いていない）なら、**その記録だけについてもう一度聞く**。
    先生があとから課題にチャレンジを足し、端末にそのチャレンジの古い記録があったときに起きる。答えた日時は最初のまま（答えた
    あとにできた記録を、あとから「前より前」にしない）。
  - 答えが「消す」なら、聞かずに捨てる（同じパソコンで開いていた別のタブが、消す前の記録を書き戻したときに起きる）。
  - 答えたあとにできた記録は、そのまま送る（「前」にしない）。
- ［消す］で空にするのは**端末のレッスンの記録だけ**（localStorage `smalruby:lessonProgress`）。はじめて開いたチャレンジの
  スポットライトの記録・作品・ほかの設定は消さない。
- ×で閉じたときは答えなかったことにし、送らない。次に送るときにもう一度聞く。

### 進み具合の送り方

送る量と回数をおさえて、費用を小さくする（1 クラス 40 人 × 11 チャレンジ × 2 回（開いた・できた）≒ 授業 1 回で 880 回の書き込みまで）。

- クラスへ送るのは「**できた**」と「**チャレンジを開いた**」だけ。「正解のプログラムを確認した」はクラスには送らない。
- 送るのは、**できたとき・課題のチャレンジを開いたとき・クラスの画面を開いたとき**（まとめて）。
  **定期的な問い合わせはしない**。
- **1 回の送信は「席 × 課題」の 1 件にまとめる**（その席・その課題の進み具合をまとめて上書きする）。
  チャレンジごとに別々に送らない。
- 送るのは課題のチャレンジだけ。課題の外のチャレンジは送らない（サーバーでも捨てる）。できた時刻は過去に戻さない
  （一度できたものは消えない）。
- 端末の記録は、クラスに関係ない形（チャレンジ ID・できた日時）のまま残す。クラスへ送る分は、そこから作る。
- 送れなかったとき（通信が切れていたなど）は、次に送るときにまとめて送る。細かいところ:
  - 送るたびに、端末の記録のうち課題のチャレンジを**全部まとめて**送る（サーバーはマージし、変わらない送信は書かない）。
    だから送れなかった分を別に取っておかない。端末の記録が正で、次の送信に自然に入る（席に入り直してサーバーの行が
    作り直されたときも、端末の記録から送り直せる）。
  - 最後に送れた中身で足りているとき（「できた」も、開いているチャレンジも変わっていないとき）は送らない
    （席ごとの 1 分 20 回の上限を無駄に使わない）。送信中にまた送るときが来たら、送信のあとに 1 回だけ送る。
  - 失敗の扱い: 通信の失敗・400（1 分 20 回の上限など）・409・5xx は、何もせず次に送るときを待つ（その場でくり返さない）。
    401 / 403 / 404 / 410（セッションの期限切れ・kick・課題が無い）は、そのセッションでは送るのをやめる。端末の記録は残す。
  - できた日時が読めない・2020 年より前の記録（パソコンの時計が戻っていたときなど）は送らない。サーバーは 1 件でもそういう
    日時があると送信ごと 400 で拒み、ほかの記録まで送れなくなるため。開いた日時がそうなら current も付けない。
  - 「いまやっている」（current）は、課題のチャレンジを開いているときだけ送る。閉じたときに `null` は送らない
    （先生の表は「できた」を優先して見せる）。
  - クラスの画面を開いたときのほか、課題に参加したとき・参加したままページを開き直したときも 1 回送る（取りこぼしの追いつき）。

### GA の計測の方針

クラスの進み具合とは別に、**レッスン全体**（課題の外もふくむ・クラスに参加していないときもふくむ）の使われ方を
GA で計測する。目的は、**人気のないコンテンツ**と**滞在の長いヒント**を見つけて見直すこと。

- 計測するもの: チャレンジを開いた・できた・ヒントのページ（何ページめか）と滞在時間・正解のプログラムを確認した・
  レッスンをおえる など。
- **ヒントの滞在時間**は、ページごとに、**そのページを開いてから、次のページへ進む・閉じる・「できた！」になる
  まで**の時間。
- **個人を特定する ID は送らない**。席番号・ニックネーム・セッションも送らない。課題や参加コードの ID も送らない。
  送るのはコース・レッスン・チャレンジの ID とページの番号くらいにする。
- イベントの名前と項目は [`README.md`](README.md) の「GA の計測」。

## 中 2 のコース「チャットをつくろう」

中学 2 年の技術分野「双方向性のあるコンテンツのプログラミングによる問題解決」の授業のためのコース。
ブロックで、チャットのアプリを作りながら、順次・反復・分岐、データとイベント、メッシュでの通信を学び、
最後に自分で工夫したチャットを作品として提出する。

設計の出発点（[EPIC #1616](https://github.com/smalruby/smalruby3-editor/issues/1616)）: 授業でワークシートを使ったら、
スモウルビーの基本操作やメッシュの使い方がわからず、自分の課題解決に進むところで生徒の手が止まった。基本と
メッシュの基本をレッスンで身につけてから、自分の課題解決に進めるようにする。

### コースの位置（前提にするもの）

- **「きょうからプログラマー」を前提にする**。そこで身につくこと（ブロックの置き方・きっかけ・見た目・音・
  条件と入力・変数・メッセージ・リストの基本）は、このコースでくり返さない。
- **小学 5 年の算数のコース（図形を描く）を前提にする**。図形（ペン）はこのコースに入れない（別のコースで学ぶ）。
- このコースで扱うのは、前提のコースで済まないこと: 手順をアクティビティ図で表す・読む、データとイベントの
  組み合わせ、**メッシュの基本**（グループ・合図・共有する変数）、チャットを作って改良すること。
- 作品の提出に[段 2](#段-2-クラスの課題とレッスン)の仕組みを使うので、このコースは段 2 のあとに出す。

### 5 つのレッスン

| レッスン | 名前 | めあて・あらまし |
|---|---|---|
| 1 | 手順を図にしよう | チャットの題材で、順次・反復・分岐を使い、アクティビティ図を読む・書く。「読んで作る」チャレンジを 1 つ入れる |
| 2 | データとイベント | 乱数・タイマー・分岐を組み合わせる（おみくじ・タイマー・じゃんけんなど） |
| 3 | メッシュでつながろう | メッシュのグループ（ホストになる・参加する）、メッシュの合図、共有する変数 |
| 4 | チャットを作ろう | 1 回送る → くり返し送る → おたがいに送る → グループチャット → ダイレクトメッセージ、と少しずつ育てる |
| 5 | チャットを改良しよう | 改良のテーマを 1 つずつチャレンジにし、生徒は 1 つ以上を選んでやる。最後に自由に工夫して作品を提出する |

- **チャレンジの中身（課題・パレット・答え・ヒント・判定・アクティビティ図・クイズ）は、レッスンごとに、実装の前に
  人間と artifact で詰める**（「きょうからプログラマー」のレッスン 1 と同じ進め方）。ここには、どのレッスンにも
  共通の決まりだけを書く。
- **1 つのレッスンのチャレンジは 5 個まで**（このコースだけの例外。ほかのコースは 3〜4 個）。レッスン 4 は 5 段で
  育て、レッスン 5 は改良のテーマが 5 つある。
- **レッスン 4・5 は、前の段のプログラムを入れた状態で始める**（`setup` で入れる）。生徒はそこに 3〜5 ブロックを足す。
  1 つのチャレンジを 5 分・3〜5 ブロックの大きさに保ちながら、チャットを少しずつ育てるため。
- レッスン 3・4 のメッシュのチャレンジは**ペアでやるのが基本**。ひとりのときは練習相手（下）を使う。
- **チャレンジを変えても、メッシュの接続は保つ**（グループに入り直さない）。チャレンジごとに 2 人で入り直すのは
  授業の時間がかかるため。できるかどうかは練習相手の実装で確かめ、できないときはチャレンジごとに入り直す形にする。
- レッスン 5 の改良のテーマ（パスワード・通知と既読・NG ワード・タイマー・スタンプなど）は、1 つずつチャレンジにし、
  その先は生徒ごとに工夫できるようにする（「できた」の判定は下の[「作品の提出」](#作品の提出)）。
- **レッスン 5 は、テーマを 1 つ以上「できた」にすれば ✓**（全部のテーマをやらなくてよい）。「レッスン 5 ぜんぶ
  できた！」・コースの ✓ も、これに従って数える。テーマは生徒が選ぶもので、全部やることを求めないため。
- プロトコル・IP アドレスなどの知識は、課題の説明やヒントで少しふれ、ふりかえりのクイズ（下）で確かめる。
  知識だけを教えるページは作らない。

### アクティビティ図

プログラムをブロックだけでなくアクティビティ図でも表せるようにする。**見る・読んで作る・描く**の 3 つ。

- **見る（最初に提示する）**: チャレンジの答えのプログラムから、アクティビティ図を自動で描く。
  - 出すのは**課題の全文**（課題の帯にマウスを乗せたときの全文）と、**ヒントの 1 ページ目**。ヒントのページごとには
    描かない（情報が多すぎるため）。
  - 描くのは SVG。スクリーンショットは使わない（[段 1 で入れないもの](#段-1-で入れないもの入れないと決めたもの)と同じ理由で、
    答えのプログラムから描けば古くならない）。1300×600 で課題の全文の中に収まる大きさにする。
  - 記号は、アクティビティ図の基本の記号（開始・終了・処理・分岐・合流・くり返し）にする。**記号の正はここ**で、
    私たちのワークシートもこの記号を使う（ワークシートは学校ごとに変わりうるので、ワークシートに合わせない）。
  - メッシュのチャレンジは、送る人と受け取る人を分けたスイムレーンで描く。
  - **図のもとのデータ**: 自分のレーンは答えのプログラム（`code` と `spriteCodes`）から描く。相手のレーンは、
    練習相手の定義（ボタン・自動の返事。下の[「メッシュの練習相手」](#メッシュの練習相手)）から描く。練習相手の
    定義はデータだけなので、図のための項目を別に足さなくてよい。練習相手の定義が無いチャレンジは、自分のレーンだけを描く。
  - 対応するブロックから始め、対応していないブロックは「処理」の箱にブロック名を書く。
  - 図を出す・出さないは、チャレンジの定義で選べる（読んで作るチャレンジでは必ず出す）。
- **読んで作る**: チャレンジの 1 つの形。**説明とアクティビティ図だけで指示する**。生徒はやれるだけやってみて、
  最後に自分のプログラムと答えを見くらべて確かめる。パレットはふつうのチャレンジと同じ。「できた」の判定もほかの
  チャレンジと同じ（`uses` / `result`。プログラムの形は見ない）。
  - **ヒントは 3 ページだけ**: ① 図と説明（チャレンジを始めたら自動で開く）→ ② 試すページ → ③ 答えを見るページ。
    1 ページ目で、最後のページに答えがあることを伝える。
  - **答えを見るページ**は、答えのプログラムを吹き出しの中に本物のブロックで描くだけで、**生徒のプログラムを
    置き換えない**。読んで作るチャレンジには「正解のプログラムを確認する」（置き換え）を置かない。置き換えると、
    そのまま動かすだけで「できた」になり（[チャレンジ](#チャレンジ)の判定の決まり）、自分で読んで作る意味が
    なくなるため。答えを描くのは、いまのヒントの絵（`steps[].blocks`）と同じ描き方なので、新しい画面は要らない。
  - [ヒント](#ヒント)の決まりとの関係:
    - **そのまま当てはめる**: 1 ページ目を自動で開く。試すページは答えのページの手前（答えを見る前に試してもらう）。
      ドラッグで動かせる・できたら閉じる。
    - **当てはめない（例外）**: 帽子のブロックを置く手順を抜かさない・絵は置いてほしいブロックを並びのまま描く・
      つなげる相手もいっしょに描く。どれも手順のページの決まりで、読んで作るチャレンジは手順のページを持たない
      （図を読んで自分で組み立てるのがねらいのため）。
    - 答えを見るページの絵は、スクリプト全体を描いてよい（「描くのは相手と置くブロックまで」の例外）。答えと
      見くらべるには全体が要るため。
- **描く**: ブロックを右クリック →「アクティビティ図」で、そのスクリプトの図をポップアップに描く。見るための
  描く部品を使う。大きい作業なので、**コースを完成・リリースしてから**取りかかる（それまでは作らない）。

### メッシュの練習相手

メッシュのチャレンジを**ひとりでも**できるようにする。ペアがいるときは本物のメッシュでやるのが基本。

- **ブラウザの中で折り返す「にせのメッシュの相手」**。メッシュの送受信をサーバーに出さずにブラウザの中で折り返す
  練習のモードで、相手を 1 人ぶん置く。ローカルで動き、レッスンに特化した軽いものにする。
- チャレンジ中、ステージの横に小さな**練習相手のパネル**を出す。相手の名前と、ボタンが 2〜3 個。ボタンを押すと、
  相手がメッシュで合図を送った・共有する変数を変えたのと同じことが起きる。1300×600 での並べ方は練習相手の実装で
  決める。パネルを出す・消すときにステージの列が動くなら、[課題バー](#課題バー)の `resize` の決まりに従う。
- **自動の返事**: 「合図 X を受け取ったら Y を送り返す」のような簡単な決まりで、相手が返事をする。
- **定義はデータだけ**。チャレンジの定義に相手の名前・ボタン・自動の返事を書けば動き、チャレンジごとにコードを
  書かない（チャレンジごとに作り込まない）。
- 「できた」の判定は、本物のメッシュと同じ事実として数える（判定のしくみは変えない）。
- パネルを閉じれば、同じチャレンジを本物のメッシュ（ペア）でできる。
- 作らないもの: サーバーにいる相手（ボット）、AI の返事、2 台目のスモウルビーを丸ごと動かす仕組み。
- メッシュはいちばん大事な機能なので、練習のモードを足すときはメッシュのデグレの確認をする。

### ふりかえりのクイズ

- チャレンジができたときの**「できた！」の表示の中**に、**3 択のクイズ**を出せるようにする（「レッスン n ぜんぶできた！」
  「課題クリア！」の表示でも同じ）。チャレンジの定義に問い・3 つの選択肢・正解・解説を書くだけで出る。
  文言は en / ja / ja-Hira。
- ヒントの中には置かない。「できた」になるとヒントの吹き出しは閉じる（[ヒント](#ヒント)）ので、ヒントの中に置くと、
  自分でできた生徒ほどクイズを見ない。「できた！」の中に出せば、できた生徒の全員が見る。
- 選ぶと、正解／はずれと解説を出す。**何度でも選び直せる**。
- **「できた」の判定には入れない**（できたあとに出るので、答えは「できた」に関係しない）。答えなくても「次のチャレンジへ」
  などのボタンで先へ進める。

### ワークシートとのリンク（片方向）

- **ワークシートからスモウルビーへリンクする**。ワークシートの各ページに、やるレッスン・チャレンジの名前とリンクを書く。
  ワークシートの前半に当たる基本をレッスンで終えてから、自分の課題解決のページに進む流れにする。
- **スモウルビーからワークシートへはリンクしない**。ワークシートは学校ごとに変わるため。コースの定義にワークシートの
  URL や名前を持たない。生徒にワークシートを示したいときは、先生がクラスの課題の説明に書く。

### 作品の提出

- **段 2 の「作品の提出もする」課題の仕組みで出す**。このコースのための提出の仕組みは作らない。
- 先生はレッスン 5（とそれまでのレッスン）を紐付けた課題を作り、「作品の提出もする」を ON にする。課題クリアの
  あと、「課題クリア！」・課題の帯・クラスの画面の案内（自由にプログラムを作って提出しよう）から提出する
  （[課題クリア](#課題クリア)）。
- 改良のテーマのチャレンジは、それぞれ最低限を学ぶところまでを「できた」の判定にする。その先の工夫は判定せず、
  提出した作品で先生が見る。
